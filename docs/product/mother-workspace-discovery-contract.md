# Ticket 06: explicit Personal access, then read-only workspace discovery

The isolated Owner rebuild has **two separate** Owner-session + Origin + double-submit CSRF actions for a selected saved mother: `POST /api/owner/v1/mother-accounts/{accountId}/personal-session` for password+TOTP Personal session refresh, then `POST /api/owner/v1/mother-accounts/{accountId}/discovery` for read-only accounts/check discovery. GET on either path only reads saved state. Account import/save, GET, and selecting a mother never log in or discover. Even one returned space needs a further explicit target choice. The target choice is not an operational binding or permission grant.

`platform.PersonalWebRefresher` uses only first-party HTTPS hosts for every request and redirect hop, including redirects returned by the reused target login helpers. It establishes a fresh cookie jar and device ID, submits password and the challenge-bound TOTP, fetches `/api/auth/session`, and checks the returned Personal Web AT's source client ID, scopes, post-TOTP AMR/MFA, consistent nested/flat account identity and plan, positively supported Personal plan (`free`, `plus`, `pro`, `personal`, `default`), and expiration before sealing the generation. Conflicting claim representations or Workspace-scoped plans fail closed. This claim parsing is an admission hint, **not signature verification**; the fresh authenticated session GET and subsequent accounts/check read remain the platform responses. If the source flow requires a Personal account-selection POST, the current refresher **fails closed** rather than selecting any account or Workspace on behalf of the Owner. It never runs the target's Workspace-selected delivery OAuth flow, requests RT, sends invitations or invokes other account operations.

The canonical mother's saved password and optional TOTP are also AES-GCM encrypted using a versioned envelope, the same deployment key ring, and mother ID+credential revision+secret field as associated data. On `migrate` (which now requires `TSW_TOTP_KEYRING_FILE`) and before Owner routes or workers start, an exclusive-lock transaction converts legacy plaintext source rows and commits a durable marker. Missing keys, malformed material or plaintext after that marker fail closed; there is no post-startup plaintext fallback. Deployments with separate migration/control database roles must grant the control role access to the new marker table (read, and insert if control can perform first-start conversion) alongside its existing credential-table permissions. Owner create/import/update seal before writing; explicit Owner export and Personal refresh or existing authorized workspace-read/removal workers decrypt just in time. Only a confirmed Owner export may return source material in the existing TXT format. The Personal AT, session cookie names/values and device ID are AES-GCM encrypted with the deployment key ring and mother ID+credential revision as associated data. Secrets never appear in the Owner response except that explicitly confirmed export. The credential generation, expiry, Owner session rotation and persisted refresh status are scoped to the selected mother. Missing/invalid saved password or 2FA is `missing_credentials`; explicit password/TOTP 401 is `invalid_login`; other refresh errors are `refresh_failed`. A refresh reservation revokes prior Personal session and visibility, and a failed refresh cannot restore them. A new attempt or source material revision fences an older response.

`platform.AccountsCheckDiscovery` implements the sourced, **read-only** fixed-host `GET https://chatgpt.com/backend-api/accounts/check/v4-2023-04-27?timezone_offset_min=-480` with saved Bearer Personal AT, session cookies and device ID. It blocks redirects, caps responses, strictly parses the accounts map, case-folds personal/free/default exclusions (including account ID), allows only supported Team/Business plan and Workspace/Team kind combinations, fails closed on unknown plans/kinds, deduplicates platform workspace IDs, and distinguishes valid empty from 401 `session_expired`, 403 `permission_denied` and transport/parse/server `discovery_failed`. Discovery never falls back to a password login. `NewControlHandlers` wires both explicit actions to the **same admission policy** via `egress.Manager.Acquire`; each action obtains and releases its **own** lease. Neither action uses `http.DefaultClient` or an Owner-supplied URL. This is production-capable wiring, **not evidence of successful live platform access**: all tests use mock RoundTrippers; no live request or deployment was performed.

No DB transaction or row lock spans either remote attempt. Short reservation and completion transactions use monotonically increasing per-mother attempt numbers, source credential revision and Personal generation UUID to reject late, stale and cross-generation results. A failed/empty attempt clears old visibility at reservation. `tsw_mother_personal_sessions` stores Personal generations separately from the mother's source materials and Workspace OAuth. `tsw_mother_workspace_visibility` stores each mother's observed access to the canonical workspace entity, not the operational `tsw_mother_workspace_bindings`. Credential rotation or disabling deletes the sealed Personal generation and per-mother access/visibility/discovery rows in the same transaction; expiry before or during discovery reports `session_expired` and revokes the exact generation under the attempt fence. GET reads status and visibility from one repeatable-read snapshot so attempt changes cannot mix facts. Failed/empty discovery and observations older than seven days invalidate displayed candidates. Visibility never proves management permission or subscription, seat, member or invitation facts; **do not use visibility to execute tasks**.
